# アプリ化の計画（未着手）

koe-matome をアプリにして、コマンドを打たなくても使えるようにする計画。
**データは配らず、アプリが使う人の端末で取得する**という今の原則はそのまま守る。

## 前提：なぜアプリなら「各自で取得」ができるのか

- ブラウザのページ（公開サイト・PWA）は、よそのサイトからデータを取ることをブラウザに止められる（CORS）。
  そのため公開サイトにすると、サーバーからデータを配るしかなくなる。これはストア規約第8条（第三者への公開）の点でグレーなのでやらない。
- アプリ（Tauri・Capacitor）は端末側の通信機能でストアを読めるので、ブラウザの制限を受けない。
  CLI 版と同じく「その人の端末が、その人のために公開ページを読む」形になる。

## 守ること（CLI 版と同じ）

- 取得は1秒1件、並列なし。間隔は設定で短くできないようにする
- サイトマップの更新日時で差分だけ取得する。推しに絞った取得を基本にする
- 公開ページだけを読む。ログインや `/mypage` には触れない
- 取得したデータは端末の中だけに置く。アプリからサーバーへは何も送らない
- アプリ名・アイコン・紹介文に、タレント名・ロゴ・公式画像を使わない。非公式であることを明記する

## 構成

1. **取得と読み取りの規則を TypeScript に移す**（`core/`）
   - `sites/nijisanji.py` と `catalog.py` の処理（メンバー一覧、英語表記、サイトマップ、商品の取得、販売期間、担当ライバーの判定、卒業生の登録）
   - 通信処理は差し替えられるようにする（Tauri の HTTP プラグイン、Capacitor の CapacitorHttp）
   - Python 版のテストケースを JSON に書き出し、両方で同じ結果になることを確かめる（規則の食い違いを防ぐ）
   - Python の CLI はそのまま残す
2. **画面は今の `template/page.*` を使う**
   - 埋め込みデータの代わりに、アプリ内の保存先（IndexedDB など）から読む
   - 「更新」ボタンと進み具合の表示、推しの選択を足す
   - 購入記録・ファイルのドロップ取り込み・引き継ぎコードはそのまま使える
3. **包み方**
   - PC：Tauri（Mac / Windows / Linux）。GitHub Releases で配る。自動更新は Tauri のアップデーターを使う
   - Android：Capacitor。APK を GitHub Releases で配る
   - iOS：Capacitor。配るには App Store の審査が必要（下の「リスク」）

Python を丸ごと同梱する方法（PyInstaller を Tauri から呼ぶ）もあるが、アプリが重くなり、スマホでは使えないので採らない。

## 進め方

| 段階 | 内容 | 終わりの目安 |
|---|---|---|
| 1 | `core/` を TypeScript に移し、Python 版と同じテストが通る | 同じ商品キャッシュから同じ `voices.json` ができる |
| 2 | Tauri の PC 版。推しを選んで更新し、一覧が出る | Mac で初回取得から購入チェックまで通る |
| 3 | Android 版（APK） | 実機で取得・表示・引き継ぎコードが動く |
| 4 | iOS 版 | 審査に出すかは、その時点で判断する |

## リスクと決めていないこと

- **ストアの構造が変わったとき**：アプリの更新が要る。CLI の `git pull` より届くのが遅い。アップデーターで補う
- **使う人が増えたときのストアの負担**：推しに絞った取得、差分更新、販売中の商品を取り直すのは30日ごと、の3つで抑える
- **スマホの初回取得**：推し1人で約2分かかる。iOS ではアプリを開いたまま待ってもらう（裏で動かし続けられない）
- **iOS の審査**：他社の権利に関わる内容のアプリは、許可がないと断られやすい。App Store に出すなら ANYCOLOR への問い合わせが先
- **署名**：Mac の公証には Apple Developer Program（年額）が要る。ないと起動時に警告が出る。Windows も署名なしだと SmartScreen の警告が出る
- **ストア配布か野良配布か**：未定。まずは GitHub Releases での配布を想定する
